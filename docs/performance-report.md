# ZYX 性能测试报告

> 测试日期：2026-10-31 · 对应提交：M5 字节码虚拟机

ZYX 的字节码虚拟机后端在 6 组测试中，耗时是 CPython 3.12 的 0.99 到 2.99 倍：高阶函数用例与 Python 持平，循环用例只慢 14%，差距最大的是筛法（2.99 倍）。作为对照，最初的树遍历后端是 Python 的 1.4 到 7.0 倍。虚拟机相对树遍历后端提速 1.4 到 4.8 倍。

![ZYX 与 Python 的耗时倍数](images/benchmark.svg)

## 1. 测试环境

| 项目 | 配置 |
|---|---|
| CPU | Intel Core i9-14900HX |
| 系统 | Windows WSL2，Linux 6.18（glibc 2.39） |
| Python | CPython 3.12.3 |
| ZYX | Rust 1.97.1 编译，`opt-level=3`、`lto=true`、`codegen-units=1` |

## 2. 测试方法

### 2.1 测试用例

每个用例由一个 ZYX 脚本（`bench/zyx/`）和一个逐行对应的 Python 脚本（`bench/py/`）组成。两者算法、数据规模和输出完全相同，主体都写在函数中运行。

| 用例 | 内容 | 主要考察 |
|---|---|---|
| `fib` | 递归计算 `fib(35)`，约 3000 万次调用 | 函数调用与返回 |
| `loop` | 3000 万次 `while` 循环中做取模、乘、减、累加 | 循环控制与整数运算 |
| `sieve` | 埃氏筛求 200 万以内素数，重复 5 轮 | 数组读写、内存访问 |
| `strings` | 200 万次字符串插值，`join`、`split`、`ends_with`，2 万次追加拼接 | 字符串创建与内置函数调用 |
| `structs` | 1000 个粒子结构体模拟 5000 步，每步读写 4 个字段 | 结构体字段访问 |
| `functional` | 对 300 万个元素做 `map`、`filter`、`sort`、`reduce`，回调为匿名函数 | 高阶函数与闭包调用 |

### 2.2 计时方式

- 命令：`make bench`（即 `python3 bench/run_bench.py`）。
- 每个用例对 Python、ZYX 树遍历后端、ZYX 虚拟机后端各运行 5 次，取墙钟时间的中位数，包含进程启动时间。
- 运行器逐一比对 ZYX 与 Python 的标准输出，任一不一致即标记失败。本次全部一致。
- 原始数据见 `bench/results.md` 和 `bench/results.json`，图表由 `bench/plot.py` 生成。

## 4. 优化过程

先完成树遍历后端，让全部测试通过，再实现字节码虚拟机并逐轮优化（ADR-0002）。每一轮都先用 valgrind 的 callgrind 工具统计各函数和源码行的指令数，找到热点再动手；每轮结束后两个后端都要通过全部 101 个黑盒测试。

下表为各轮结束时虚拟机耗时相对 Python 的倍数，各轮原始数据在 `bench/history/`。

| 用例 | 树遍历基线 | 第 1 轮：虚拟机初版 | 第 2 轮：超级指令 | 第 3 轮：缓存、内存与调用 |
|---|---|---|---|---|
| fib | 5.84 | 3.24 | 1.70 | 1.60 |
| loop | 4.82 | 2.93 | 1.24 | 1.13 |
| sieve | 6.96 | 5.15 | 3.49 | 2.94 |
| strings | 1.95 | 1.69 | 1.62 | 1.80 |
| structs | 5.71 | 4.01 | 3.10 | 1.49 |
| functional | 1.53 | 1.37 | 1.04 | 1.00 |

### 第 1 轮：字节码虚拟机初版

把槽位解析后的中间表示编译为栈式字节码。ZYX 函数之间的调用改由虚拟机自己的调用帧栈管理，不再递归调用 Rust 函数，平均提速约 1.6 倍。

### 第 2 轮：超级指令与窥孔优化

callgrind 显示，`loop` 每轮迭代要执行 19 条字节码、约 1080 条机器指令，主要开销是值栈的反复压入和弹出。编译器在生成指令时做窥孔合并，把常见的指令组合并成一条：

| 原指令序列 | 合并后 | 典型源码 |
|---|---|---|
| `GetLocal b` + 二元运算 | `BinLocal(op, b)` | `a * b` |
| `Const c` + 二元运算 | `BinConst(op, c)` | `i % 7` |
| 比较 + `JumpIfFalse` | `JumpIfNot(op)` | `if a < b` |
| `GetLocal a` + `GetLocal b` + 比较 + 跳转 | `JumpIfNotLL(op, a, b)` | `while i < n` |
| `GetLocal x` + 右值 + 运算 + `SetLocal x` | `OpAssignLocal(op, x)` | `total += e` |
| 下标或字段访问的对象是局部变量 | `IndexLocal`、`SetIndexLocal`、`FieldLocal`、`SetFieldLocal` | `flags[j] = false` |

另外，语句位置的 `if` 不再压入、弹出一个无用的值。合并后 `loop` 的循环体只剩 8 条指令：

```text
   4  JumpIfNotLL(Lt, 2, 0, 12)      ; while i < n
   5  GetLocal(2)                    ;   i
   6  BinConst(Mod, 2)               ;   % 7
   7  BinConst(Mul, 3)               ;   * 3
   8  BinConst(Sub, 4)               ;   - 1
   9  OpAssignLocal(Add, 1)          ;   total += ...
  10  OpAssignLocalConst(Add, 2, 5)  ;   i += 1
  11  Jump(4)
```

合并必须保证不改变语义，所以有两条约束：一是有跳转落在被合并的指令中间时不合并；二是右值含有块、`if`、`match` 时不合并，因为这些表达式可能给同一个局部变量赋值，合并后读取变量的时机会改变。可以用 `zyx --dis 文件` 查看编译出的字节码。

### 第 3 轮：内联缓存、内存布局与调用路径

| 优化 | 依据（callgrind） | 效果 |
|---|---|---|
| 字段访问内联缓存：每条字段指令记住上次遇到的结构体类型和字段下标 | `structs` 中按名字查找字段占 30% | `structs` 0.96 s → 0.48 s |
| 条件中的 `and` / `or` 直接编译为短路跳转 | 原先要先算出布尔值再判断，多出 4 条指令 | 条件判断更短 |
| 值从 24 字节压缩到 16 字节：字符串改用 `Rc<String>`，区间改为装箱 | `sieve` 的瓶颈是 200 万元素数组的内存访问 | `sieve` 1.53 s → 1.31 s |
| 局部变量独占字符串时原地追加 | `s = s + "x"` 每次复制整个字符串 | 避免 O(n²) 拼接 |
| 内置函数复用参数缓冲区 | 每次调用 `push`、`len` 等都分配一个参数数组 | 每次调用少一次内存分配 |
| 调用时把被调函数从栈上移出，而不是复制引用 | 每次调用多一对引用计数操作 | `fib` 小幅提升 |
| 覆盖整数、布尔等值时跳过析构 | 析构函数调用未被内联 | `loop` 1.12 s → 1.08 s |

热路径上用到 `unsafe` 的地方只有两类，每处都写了安全性说明：

- 取指令、读写局部槽位、读常量时不做边界检查。这些下标都由编译器生成，必然合法；调试构建中仍用断言检查，101 个测试在调试构建下同样通过。
- 调用帧用裸指针引用代码块。代码块在虚拟机创建时生成，之后既不修改也不释放。

第 3 轮也有代价：字符串改用 `Rc<String>` 后，每创建一个字符串要分配两次内存，`strings` 从 1.62 倍退到 1.80 倍。考虑到其余 5 个用例都受益，保留了这一取舍。

## 5. 差异原因分析

| 用例 | 虚拟机倍数 | 主要原因 |
|---|---|---|
| functional | 0.99 | 遍历、排序都在 Rust 实现的内置函数里完成，解释器只负责执行简短的回调函数，两边的主要开销都在原生代码中 |
| loop | 1.14 | 超级指令把循环体压到 8 条指令，与 CPython 3.12 的特化字节码接近；剩余差距在指令分发和 16 字节值的搬运 |
| structs | 1.57 | 内联缓存消除了字段查找；结构体字段放在 `RefCell<Vec<Value>>` 中，每次访问都有借用检查和一次间接寻址 |
| fib | 1.61 | 每次调用都要建立调用帧（检查参数个数和调用深度、扩展值栈、压入帧记录）并维护引用计数；CPython 3.12 的调用路径经过专门优化 |
| strings | 1.77 | 每个字符串要分配两次内存（`Rc` 和 `String` 缓冲区），而 Python 只分配一次；`split` 的 200 万个子串放大了这一差距 |
| sieve | 2.99 | ZYX 每个数组元素 16 字节，Python 列表元素是 8 字节指针，筛法跳跃访问内存时 ZYX 的缓存未命中更多 |

树遍历后端慢的原因：每个节点的求值都要递归调用 Rust 函数并返回较大的 `Result`，控制流（`break`、`return`）也借助错误通道传播。它主要作为语义参考实现保留，用于和虚拟机做差分对照。

## 6. 后续优化方向

以下优化在本阶段没有做，按预期收益排序：

1. **NaN-boxing**：把值压缩到 8 字节，预计 `sieve` 和 `loop` 可以追平或超过 Python，但需要重写值的表示，改动最大。
2. **单次分配的字符串类型**：引用计数和字符数据放在同一块内存里，预计 `strings` 提升 20% 到 30%。
3. **精简调用路径**：调用帧瘦身，参数个数和深度检查合并，热点函数调用内联缓存，预计 `fib` 提升 10% 到 20%。
